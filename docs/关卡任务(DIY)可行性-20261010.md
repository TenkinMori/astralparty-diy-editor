# DIY 关卡「设置任务」可行性调查（2026-10-10）

> 用户原话：**「这里怎么没有设置任务的功能」**。
> 拍板结果：**先不做，只要知道原因**。本文只存档结论，方便以后要动时直接开工。
> 调查方式：只读反编译源码 + 只读服务端 + 8898 上真服务端进程 + 真 TCP 帧实测（未改任何代码）。

---

## 一、一句话结论

**DIY 房本来就有任务**，用的是**底版那一档的官方任务**（实测 `我的关卡`（底版 `82016_4`）拿到 `[321140,321150,321160,321170,321180]` 5 条，与同图同档普通房逐条相同）。
编辑器里"找不到设置任务"是因为**这个功能确实还没做**；而**路 C（从底版官方任务里勾选）随时能落地**，且**一个客户端文件都不用动**。

## 二、机制：任务名单是谁定的

### 客户端：面板是**服务端驱动**的，客户端不从自己表里选任务
* 面板 `UI/UIBattleInfo_Com_PVEProgress.cs`：`UpdateTaskStatus()` :254-270、`RendererTaskInfo()` :279-300。
* 数据源 `GameLogic/BattleLogic.cs:3975 GetMapMissionsData()` → `room.curRoomInfo.MapMissionDict`。
* 填充 `GameLogic/RoomInfo.cs:510 UpdatePVEData()` → 遍历 `info.MapMissions`（**Room 字段 50**）→ `RoomInfo.cs:53-58 UpdateMapMission()`。
* ★ **建对象不看表**：`RoomInfo.cs:53-58` 对任何 id 都 `new MapMissionData()`；`MapMissionData.cs:69-76` 用 `Type.GetType($"GameLogic.MapMissionTargetData_{MissionId}")`，**找不到就回落基类** ⇒ 陌生 id 不在这里报错，**只在渲染时炸**。
* 协议：**`MapMissionNotifyS2C = 1072`**；`Room.MapMissionsFieldNumber = 50`。
* 客户端**唯一**"按自己表定任务名单"的地方是教学专用：`Core.Tutorial/TutorialBoardMissionManager.cs:635-664`（只被 `TutorialBoardManager.cs:410` 引用）。
  ⇒ `MapMission_330010` 那种"按 id 反推"**跟正式任务不是一条路**（它自己 `new MapMissionNotifyS2C` 发回服务端，`MapMission_330010.cs:391-414`）。

### 服务端（测试服）：名单来自 `Map.bin` 难度行的 `pve_missions`
* `battle.py:442-456 mission_progress(room)`：`gamedata.map_difficulty_row(room["map_id"], levels.room_difficulty(room))` → `row["pve_missions"]`。
* 解析：`gamedata.py:293-294`（`a==4 and b==2 → pve_missions`）、`gamedata.py:330 map_difficulty_row()`；本体 `PVEMission.bin`（`gamedata.py:1002-1021`）。
* 下发：开局 `payloads.py:1117-1118`（`pb_b(50, mission(*item))`）；中途 `handlers.py:3827-3832 push_missions()`（调用点 `:3569` 轮次末、`:4875`）。

### DIY 今天的实际行为
`levels.py:297-316 for_room()`（DIY 优先）→ `levels.py:319-329 room_difficulty()` → `diylevels.py:726-742 table_difficulty()`（用 `diy.base_level` 解底版档号）→ 查 `Map.bin`。
`diylevels.py:451-528 _normalize()` **没有** `pve_missions` 键 ⇒ **名单 100% 由底版那一档决定**，也就是**作者的 `base_level` 已经在决定任务名单**。

实测（8898，真服务端 + 真帧）：

| 房间 | Room.MapMissions(50) |
|---|---|
| DIY 底版 `82016_4` | `[321140, 321150, 321160, 321170, 321180]` |
| DIY 底版 `82016_0` | `[321100, 321110, 321120, 321130]` |
| DIY 真关卡 `我的关卡` | 同 `82016_4` 那 5 条 |
| 普通房 `82016/4`、`82016/0` | **与同档 DIY 逐条相同** |

## 三、能不能自定义任务：三条路

**先钉死一条**：**客户端不认自定义任务 id，而且不是"不显示"是抛 NRE** ——
`UI/UIHelper.cs:567-575 GetPVEMissionInfoConfigure()` 查不到返回 `null`；`GameLogic/MapMissionTargetData.cs:17/29/38`（`GetTitle/GetProgressDesc`）与 `UI/UIBattleInfo_Com_PVEProgress.cs:284-288` 都是**直接解引用**。客户端表里官方 101 条任务 id 全在。

| 路 | 能做到吗 | 依据 / 代价 |
|---|---|---|
| **A · 纯服务端自定义 id** | ❌ **做不到** | 就是上面那条 NRE 链：id 不在客户端表 ⇒ 面板抛异常 |
| **A′ · 把任务行随内容包烧进客户端表** | ⭕ 能，机制现成 | `4-服务端\tools\nextpack.py:2278-2289 _patch_map_events()` 已经在补 `PVEMission.bin` 行（注释原文：*不补 → 任务面板上的"击倒 XXX 0/N"读不到目标与数量*），`nextpack.py:2139 NEW_PVE_MISSION_IDS` **正是那 5 条**。代价：任务 id/文案/目标要**预先烧进内容包**，每加一批任务要重发一次客户端内容包 ⇒ 与"作者现编任务"天然矛盾 |
| **B · 客户端补丁做真自定义** | ⭕ 能，成本最高 | 管线现成（`modsrc/*.cs` → `NextUi.dll` → dllpatch 的 7 种补丁含**方法体替换**）。挂点：`RoomInfo.cs:53-58`（建实例）、`MapMissionData.cs:69-76`（按 id 选子类）、`MapMissionTargetData.cs:17/29/38` + `UIBattleInfo_Com_PVEProgress.cs:284-288`（**必须一起补，否则照样 NRE**）。★ 真正的难点不是补漏，是**文案没地方放**：`MapMission` 协议体只有 `MissionId/Targets/MissionState/ExtraParam`（`MapMission.cs:36-52`），要动协议字段 |
| **C · 只从底版官方任务里勾选** | ✅ **推荐** | 客户端只认表里的 id（`UIHelper.cs:567-575`），官方 101 条都在；显示也不需要新子类（82016 极限档那 5 条**本来就没有客户端子类**，回落基类即可）。**零客户端改动** |

### 路 C 落地要点（将来要做的话）
**json 形状**（顶层，与 `progress`/`start_monsters` 平级；形状一次定好，将来升级 A′/B 不用改）：
```json
"pve_missions": { "mode": "pick", "ids": [321140, 321150, 321160] }
```
**服务端 3 处小改**（形状照既有 `progress.limit` 的口径 ⇒ **老图零影响**，"没写这个键 = 完全等于今天的行为"）：
1. `diylevels.py:451-528 _normalize()` 增 `pve_missions` 解析（只收 int、滤 ≤0、去重、保序）；
2. `levels.py` 增访问器（照 `rounds()` / `start_monsters()` 形状）；
3. `battle.py:442-456 mission_progress()`：`row["pve_missions"]` 改成"**DIY 说了就用 DIY 的，否则原样**"。

**编辑器**（`D:\小小兔趴\5-DIY关卡\src`）：
* 新块「关卡任务」：列出**底版那一档**的官方任务；读 `Map.bin` 难度行的现成范式是 `GameTables.cs:991 ProgressLimitOf()`，照它加 `PveMissionsOf(mapId, index)`（只多解析 field 4）。
* 每行显示：**文案**（`PVEMission.bin` field 4 → `MissionDescID` → `STRPVEMission`）+ **目标怪名**（`params[1:]` 过 `Monster.bin`）+ **数量**（`params[0]`）+（可选）筹码档位。
* 一个勾选框 = 一条任务，**默认全勾**（= 今天的行为）。

### ★★ 两个必须告诉作者的真坑（编辑器要做成提示）
1. **别勾到少于 3 条**：`82016` 这类开了罪证机制的图 `extra_modes=[2]` ⇒ 线索 **1003 = 累计完成地图任务、阈值 3**（`gamedata.py:873-875`、`battle.py:332`、`battle.py:352-356 missions_done()`）；任务 < 3 条则线索 1003 永远完不成，**罪证/真凶那套会卡死**（`levels.py:450+ mastermind_conf`，Skill 106713「4 条线索或第 8 回合揭露」）。
2. **任务目标怪必须在这关的怪里**：官方任务是"击倒某只怪 N 次"（例：`321140` = 击倒 `1023` 四次）。作者自己摆怪 ⇒ 板上没那种怪这条任务永远完不成 ⇒ **编辑器必须显示每条任务的目标怪**。
   （怪表集合算法可直接抄 `diylevels.py:753-806 monster_table_ids()`。）
* 小坑：`relics.py:140-153 mission_tier()` 查不到回 `None`，调用点 `handlers.py:3578` 会 `or 1` 降级成 1 档；官方 `321100~321180` 在 `server/data/relic_mission_tier.json` 都登记了，**跨图挑任务**时才会踩到。

## 四、验收方式（将来做的时候照这个验）

**服务端侧（不用客户端）**
1. `python tools\gm.py diy <关卡名>` 或建房名写 `DIY:<关卡名>`；
2. 日志出现 `DIY 房 #N（关卡 …）放行 开局`；抓 **1003** 帧里的 **Room 字段 50**，id 集合应等于勾选集合；改勾选再进一次应跟着变；
3. 任务真完成时的单发帧是 **1072**（`handlers.py:3827-3832 push_missions()` → `payloads.py:1143-1149 mission_notify()`；调用点 `:3569` 轮次末、`:4875`）。
   ⚠️ **开局那批只在 1003 里发一次**，之后没有 1072（实测），要看 1072 得等任务真完成。

**客户端侧**：进棋盘点 **`!任务`**，核对标题（如"击倒<怪名>"）与进度 `0/N`；1072 到达后走 `BattleLogic.cs:3928 OnMapMissionNotifyS2CServerCallBack` → `RoomInfo.UpdateMapMission` → `signal.mapMissionChange.Dispatch()`（`BattleLogic.cs:730-745`）刷新。
